## 2. Action layer & offline/sync architecture

**dispatch()** (use-mjengo.ts:762-877):
- share-link client → `POST /api/share` (allowlist `CLIENT_ACTIONS`, shared server-safe list in `src/shared/client-actions.ts`).
- logged-in client-role → `POST /api/actions`.
- owner online → `POST /api/actions`; on success server payload replaces state; on HTTP refusal → honest toast with server `{error}` (FE-6b, :842) + console.error; on network-level failure → **optimistic local write + outbox queue** (:845-866) with queued toast.
- owner offline → optimistic `reduceLocal()` (25+ action mirrors, :261-562) + outbox item, stamped with entity `baseVersion` (`stampBaseVersion`, :231-258 — task.*, attendance.* rows versioned). **2026-09-19 #183 audit spot-check fixed: `attendance.override` was the one server-versioned type the client never stamped (offline overrides queued without baseVersion → stale flushes applied silently, last-write-wins); it is now stamped via the row-id path, the bulk muster also stamps array-shaped records (the server accepts both shapes), and `reduceLocal` gained the `attendance.record`/`exception`/`override` optimistic mirrors so an offline muster roll / exception / override shows in the Fundis tab instead of only as a queued toast.**

**Outbox** (spec §40/§41): zustand-persisted (`mjengo-os-store` v1, migrate + partialize :1049-1077). Lifecycle pending→syncing→synced|failed|conflict; `syncNow()` drains `POST /api/sync` with per-item results; conflict metadata (REJECTED stale-version, serverVersion/baseVersion, keep-server suggestion); failed items keep retryCount + lastError, ONE manual `retryAll()` — no auto-retry loops; synced → `syncHistory` capped at 50. `resolveConflict()` keep-server (drop + reload) / keep-mine (force re-send; `server-wins` financial rows refused). UI: `sync-outbox-panel.tsx` (per-item sheet, conflict chips, retry footer; **#192: the sheet header states the device-local honesty line — queued actions live in this browser's localStorage only**). Reconnect: `setOnline(true)` auto-drains + toasts (use-mjengo.ts:743-760); **2026-09-26 #193: enqueue registers the one-shot Background Sync tag `mjengoos-outbox` (feature-detected via `registerOutboxSync`, sw-handlers) — when connectivity returns, Chromium re-launches the SW, whose `sync` handler posts `{ type: 'mjengoos:drain' }` at open clients (app.tsx container listener → `syncNow`); Safari/Firefox unchanged**. **2026-09-26 #192 (persistence hardening): the store persists through a GUARDED storage adapter (the `createJSONStorage` seam) — a failed `setItem` (QuotaExceededError / iOS private mode) is caught instead of propagating out of `set()` (which used to break the running action mid-flight while the store kept queueing silently), the non-persisted `persistDegraded`/`persistQueueOnly` flags flip, and the app-level banner renders (red = nothing reaches disk; amber = the queue-only fallback banked the queue by dropping the re-fetchable `data` slice); a later successful full write self-heals the flags. Bounding decision (documented in partialize + pinned by `outbox-persistence.test.ts`): `data` STAYS persisted (the offline boot serves it — issue #78; no photo blobs exist to strip, server reads are take-capped), the outbox stays unbounded BY DESIGN (§52 — pruning it IS data loss), and the measured size budget for a representative large project + 100 queued actions is pinned under 4 MB. Multi-tab: a `storage`-event listener rehydrates on foreign writes to the key (250 ms trailing debounce, last-writer-wins — a CRDT is deliberately not wanted: §41 + baseVersion arbitration is server-side), and rehydrate-time normalization returns orphaned `syncing` items (mid-drain snapshots) to drainable `pending`. Restart durability is pinned at the storage level (offline-queue → disk → rehydrate restores)**. **2026-09-19 #183: the conflict-resolution test matrix is complete — all 11 versioned action types (6 task + 5 attendance) run stale/fresh/absent/force arms server-side (`outbox-versions.test.ts`, incl. §41 semantic outcomes and force-refuses-server-wins financial rows), and the client chain (stampBaseVersion / bumpLocalAttendanceVersion / reduceLocal version bumps / normalizeOutboxItem migration / the second-offline-edit-stamps-newer-baseVersion invariant) is unit-pinned in `outbox-client-chain.test.ts`; a source pin in each file extracts the server's VERSIONED_*_TYPES sets so a future versioned type without coverage fails loudly.**

**Offline boot** (`offline-boot.ts`): `shouldOfflineBoot` = persisted data AND (auth gate stuck 3.5s OR unauthenticated-while-offline) → boot app shell from cache, fail-closed to Overview (role unknown offline). app.tsx:226-233 arms it; online handler nudges next-auth refetch via visibilitychange (:199-219).

**Service worker** (`public/sw.js` v3 + `sw-handlers.ts` pure fns + `tests/unit/sw-offline-shell.test.ts` / `push-routes.test.ts` source pins):
- `/api/**` network-only, never cached (:170). Non-GET untouched.
- Navigations network-first → last-good `'/'` shell (prod only; dev never caches) → precached `/offline.html` (:190-224).
- `/photos/**` cache-first, version-independent cache, LRU cap 100 with persisted recency catalog (:229-253).
- Immutable assets cache-first; `/_next/static` network-first w/ fallback (:261-312).
- Push + notificationclick: same-origin deep-link `/?projectId=`, per-project tag (payload contract pinned both sides).
- Message (`SKIP_WAITING`): the update prompt's Reload action (issue #148 / FE-11) — see the client half below.
- Sync (`mjengoos-outbox`, issue #193): Background Sync drain ping — the enqueue seams register the one-shot tag (feature-detected, Chromium); when the browser fires `sync` on connectivity recovery, the handler asks open window clients to drain via postMessage `{ type: 'mjengoos:drain' }`. A CLOSED app defers honestly to the next app open (the SW cannot read the page's localStorage outbox — a true closed-app drain needs the queue in IndexedDB, the persistence issue).

**Gaps:** ~~no Background Sync API~~ **softened 2026-09-26 via #193: enqueue registers the one-shot `mjengoos-outbox` tag on Chromium — the SW's `sync` handler asks any open client to drain when connectivity returns; a CLOSED app still defers honestly to the next app open (honest limit: the outbox lives in page localStorage the SW cannot read — a true closed-app drain needs the outbox in IndexedDB)**; ~~persistence unguarded: no quota/private-mode failure handling, no multi-tab coordination, one unbounded key~~ **hardened 2026-09-26 via #192: quota/private-mode write failures are caught at the storage adapter and surfaced (persistDegraded/persistQueueOnly → app banner), a queue-only fallback banks the mutation queue by dropping the re-fetchable data slice, foreign writes to the key rehydrate (debounced last-writer-wins), and the measured size budget is pinned — remaining honest limits: the IndexedDB move (bigger quota + the SW-readable queue a closed-app drain needs) is future work, the supplier portal's own outbox key (`mjengo-supplier-outbox`) does not yet ride the guarded adapter, and the multi-tab v1 is last-writer-wins (documented in use-mjengo.ts — no client-side CRDT by design)**; ~~supplier portal has no queue~~ **fixed via #128 — the supplier portal runs its own persisted outbox (`use-supplier-outbox.ts`, key `mjengo-supplier-outbox`) draining through the supplier-scoped `/api/sync` (SUPPLIER_ACTIONS allowlist + session-stamped `__supplierId`; the shared §40/#132/#191 core lives in `src/frontend/lib/outbox.ts`, consumed by both stores without sharing state)**; WhatsApp panel is server-dependent offline (documented in file header); offline boot with no data lands on offline.html (honest but no app).
